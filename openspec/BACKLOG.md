> 维护者：Kimi（规划）。新增功能愿望随时追加到候选清单（一行粒度），排期时才走 `/opsx:propose` 写详细规格。
> 执行顺序与依赖关系见文末批次建议；changes 的执行顺序见 `openspec/ROADMAP.md`。

## 产品愿景（2026-10-20 定稿）

**一段话**：Venera-Next 是 PC 优先的漫画阅读与收藏管理工具——发现、检索、收藏、追更、阅读在一个窗口内高效完成，键盘可全程操作；浏览与管理为效率服务，阅读为沉浸服务。

- **给谁用**：owner 本人（重度多源漫画读者）；不追求大众市场
- **核心场景**：多源检索与聚合 → 收藏与追更管理 → 长时间沉浸阅读
- **设计基调**：现代极简（浅色内容区 + 浅色壳，阅读器跟随主题不设例外），见 design-system-foundation
- **非目标**：不做内容分发/社区/账号体系；不做服务端；不内置漫画源（继承上游立场）

**愿景的用法**：新功能请求出现时先问"它服务于哪个核心场景"。三个场景都不沾的，原则上不进 backlog。

## 批次建议

- **批次 A（框架定稿后立即）**：F3 快捷键体系、F4 阅读模式方案。两者都挂在已有 changes 的延长线上，是"低成本高感知"的组合，也让执行 agent 先练熟 openspec 流程。
- **批次 B（框架验证锚点）**：F1 页面多开、F2 类 mac 预览。F1 的 propose 第一件事：验证 design-spec.md 的壳层规则能否容纳多内容栈（锚点验收）；F2 跟随 F1 定型后的导航形态。
- **批次 C（功能纵深）**：F5 收藏系列归类 ✅；剩余 F6+F7 搜索方案合并实施（共享搜索基础设施改动，一个 change 装下）。

## 锚点机制（怎么用）

锚点功能不做实现，只做框架验收：其 propose 产出的 design.md 必须包含一节"框架容纳检查"——逐条核对 design-spec.md 的 token/断点/surface/壳层规则是否需要为本次功能新增例外。需要新增例外的，先改 design-system-foundation 的 spec 再实现。这样"为未来扩展做准备"是可执行、可验收的。
